# Architecture

Ngobe is one Node.js/Bun process with no background services. Everything below runs in the CLI process; the only other process is the model server you already run.

```
 CLI (index.ts, commands.ts) ──► session.ts ──► Agent (agent.ts)
                                                 │  loop: model → validate → permission → tools → model
              ┌──────────────────────────────────┼───────────────────────────────┐
              ▼                                  ▼                               ▼
   Model gateway (llm.ts)              Tools (tools/*)                   Memory (memory/*)
   OpenAI-compatible streaming         schema-validated, timed,          SQLite: facts, runs,
   native or text tool calls           risk-classified                   failures, docs index,
   retries, idle timeout, fallback     ├─ files, grep, glob, git         prompt variants
                                       ├─ bash (process groups)
                                       └─ live knowledge (releases/*, web/*)
```

## Request flow

1. `index.ts` parses the command and options (`config.ts`), picks the UI (full-screen chat when interactive, plain lines otherwise; the chat UI is only loaded when used), and builds a session.
2. `session.ts` detects the project's stack and real commands (`project.ts`), loads `AGENTS.md`, recalls memory notes and recurring failures for this project, applies the promoted prompt variant, and builds the system prompt (`context.ts`).
3. `Agent.run` sends the conversation and the tools allowed in the current mode to the model gateway. Requests that mention versions, releases, advisories or deprecations get a freshness hint.
4. Each returned tool call is parsed, validated against the tool's JSON Schema (with the coercions small models need), checked for repeats, and passed through `Permissions`. Read-only calls in one turn run in parallel (4 at a time); anything that needs approval runs in order.
5. Tools run under a time limit with an abort signal; output is truncated head+tail; errors go back to the model as text so it can correct itself.
6. The loop ends when the model answers without tool calls, or at a limit (turns, tool calls, wall time). Cancellation (Ctrl+C) stops the current tool, answers every pending tool call, and returns.
7. The run is recorded: outcome, timings (model vs tool), tokens (reported or estimated), test results, tool events, failures.

## Model gateway (`llm.ts`, `toolProtocol.ts`)

- Speaks `/v1/chat/completions` with streaming. Retries connection errors, 429 and 5xx through the SDK (`NGOBE_MAX_RETRIES`).
- Abandons a request after `NGOBE_REQUEST_TIMEOUT` seconds without a streamed chunk (an idle timeout, so long CPU generations are not cut off).
- Tool calling: native by default. If the endpoint rejects the `tools` parameter (llama.cpp without `--jinja`, models without tool templates), it switches to a text protocol: tools are described in the system prompt and the model writes `<tool_call>` blocks. Both the JSON form and Qwen3-Coder's XML form are parsed; tool-call markup is hidden from the streamed text. Parsed calls go through exactly the same validation as native ones, and a malformed block is reported back, never executed.
- Models without a tool template (Qwen2.5-Coder) write calls as JSON in prose: in a code fence of any language, in `<function>` tags, or on a line of their own. Those are accepted when the name is a tool on offer; the text from the call on (often made-up results) is dropped, and fences are held back while streaming so the JSON never reaches the screen.
- The system prompt and tool list are byte-identical between requests, sessions and folders, so llama.cpp reuses its cache of them instead of re-reading thousands of tokens. Everything particular to a session (folder, project, commands, date, starting mode, notes, AGENTS.md) opens the first user message (`buildSessionContext`), and so does the summary after `/compact`. They used to be a message of their own with a scripted reply, "Understood.", and the 7B copied that reply as its whole answer to a question about a document. A later mode change is appended to the next message not yet sent (`modeNote`), and the freshness hint rides on the user message, so what was already sent never changes. The chat warms the cache up (`warm()`: the same request, one token) when it opens and when you start typing after a break.
- Small-model habits handled in the loop: a command handed to the user in a shell block ("run this and paste the output") becomes a `bash` call, with the usual permission check; a short reply that only announces an action ("Checking the tests.", "… Let's locate the code and fix it.") gets up to two nudges per stall to make the call instead of ending the run; "let's run the tests again" runs the test command used before (or the project's); a request for a change that ends with nothing changed gets one nudge to make the change rather than show it; a sentence saying it will run one backticked command with bash runs it; a bare acknowledgment ("Understood.", "OK") or an empty reply is asked once more, with the request quoted; giving up ("the document does not provide …", "I don't have access …") before any `glob`/`grep`/`project_overview` call gets one nudge to look in the project first; and a new file written whole in the reply (one complete code block of the right language, for a file the request or reply names that doesn't exist yet, or a generator's starter file such as `src/app/page.tsx` right after `create_project`) is saved with `write_file` instead of being written a second time (minutes on a CPU); names of technologies in the prose ("a new Next.js project") are not file names (seen live: a `tailwind.config.js` block saved as a file named `Next.js`). Asked to build or change something, a reply that writes the work as steps for the user is acted on: when the model says it will do it ("First, I'll create a new Next.js project") and a shell block of up to six commands follows, the first block runs with `bash` (servers that never exit left out) and the rest of the steps are dropped from the history; a generator command in any bash call (`npx create-next-app@latest cote-web`, which would ask seven questions nobody can answer) becomes a `create_project` call; and a reply that is still steps and code for the user ("Step 2 … Create a new file … add the following code") gets up to two nudges to do the next step with a tool.
- Falls back to `NGOBE_FALLBACK_MODEL` once when the main model is missing, unreachable or silent.
- Token usage comes from the server when it reports it, otherwise ~4 characters/token estimates (marked as estimated).
- `models()` and `probe()` back `ngobe doctor` (served models, latency, whether tool calls are native, text, or unsupported).

## Tools (`tools/`)

Every tool declares a JSON Schema, a risk category (`safe`, `network`, `write`, `exec`) that decides which modes it is offered in, an optional per-call approval level (`needs`), a time limit, and how it shows in the chat (a label like `Read`, a target, a live activity such as "Running tests", and a one-line result summary with an optional preview). Edits and writes report their real diff (`diff.ts`, through `ctx.report`): "Updated src/db.ts (+2 −1)", then the changed lines with 3 lines of context, removed lines numbered as before and the rest as after, on red and green rows with syntax colors, like Claude Code; a new file shows its first lines.

Profiles (`toolProfile`): **lean** (default) offers `read_file`, `edit_file`, `write_file`, `project_overview`, `glob`, `grep`, `bash`, `create_project`, `git_status`, `git_diff` (ask and plan modes have no shell), `check_latest_version`, `get_release_notes`, `search_security_advisories`, `fetch_url`, plus `web_search` when a provider is configured and `exit_plan_mode` in plan mode, each with a one-line description; **full** adds `multi_edit`, `bash_output`/`kill_shell` (background commands), `todo_write`, the other git tools, `check_installed_version`, `compare_versions`, `search_docs`, `remember` and `task` (sub-agents), with full descriptions. Tool results and the default page sizes of `read_file` and `grep` scale with `maxContextChars`: a tool result keeps `toolOutputLimit` characters (a fifth of the budget, 2,000–20,000), and a `read_file` page ends on a whole line within it, rather than losing its middle to the cap. A long document's page ends with the headings further on and their line numbers ("429 READINESS (chargeable)"), so the model can page straight to a section.

Claude Code conventions: files are read before they are edited or overwritten (and edits refuse a file changed on disk since), `edit_file` replaces one exact match (or all with `replace_all`) and returns the edited lines numbered, `read_file` numbers lines like `cat -n`, and a declined action ends the run and hands the turn back to the user.

Files: `tools/files.ts` lists a folder the way the project sees it (ripgrep, else `git ls-files`, else a walk that skips build and cache folders): `.gitignore`d files, `.git` and `node_modules` are left out. `glob` matches on that list (fast-glob pattern syntax via picomatch), shows the 100 newest paths and, past that, which folders hold the rest. `project_overview` (`tools/overview.ts`) reads manifests, README, the file list and the last five commits (no merges) into ~500 tokens; for a folder of projects it lists each one. A path that doesn't exist gets "Did you mean …?" with the files or folders of that name up to five levels down (`similarPaths`). `read_file` passes anything that isn't plain text through `documents.ts` (PDF via pdftotext or pdf.js, Office/OpenDocument/EPUB from their zip XML, SQLite opened read-only, archives listed, media and executables identified from their headers, ffprobe/tesseract/textutil/plutil/tar/7z when installed, private keys never shown); files over 64 MB are identified from their start. Outside the project, `read_file` needs no approval only when the user's request names the file; otherwise it asks in every mode.

Checking the work (`agent.ts`, `tools/bash.ts`, `fixups.ts`): a request for a change doesn't end with edits nobody built or tested: when files changed after the last test or build the run ran, the project's check (its test command, else its build) runs once before the run ends, and a failure goes back to the model to fix. A failed command's result starts with its key error (from the first error line, up to 14 lines, stack frames and npm notices left out) above the full output: seen live, the one real error of a `next build` sat between notices and frames. Stale framework knowledge that is always wrong for the project's versions is fixed as the file is written, with a note to the model: Tailwind 3's `@tailwind` / `tailwindcss/base` directives in a Tailwind 4 project become `@import "tailwindcss";` (seen in every live run). A reply that announces a new component without a path gets the `write_file` call with its slots as the nudge.

New projects (`tools/createProject.ts`): `create_project {framework, name, typescript?, tailwind?}` takes any framework or language name and maps it (with aliases: "next.js", "golang", "c#") to a generator whose command runs with every question answered by flags, checked against each generator's `--help` and a real run (see status.md): `create-next-app` with `--ts --tailwind --eslint --app --src-dir --use-npm --yes`, `create-vite --no-interactive` plus `@tailwindcss/vite`, `sv create` with every add-on option set (`--add tailwindcss` alone asks, then exits 0 having made nothing), `uv init`/`uv add` for Python, `go mod init`, `cargo new`, Spring Initializr over HTTP, and so on. A kind with no generator gets `mkdir` + `git init`, and the model writes the files. Afterwards the tool checks the manifest exists (a generator can exit 0 with nothing made), runs `npm install` again when a generator's install failed quietly (seen with Nest), and the agent moves into the new folder (`ToolContext.enterProject`: `config.cwd` changes, as if the user had cd'd there, and the project's stack and test command are detected again). The result says where things go, the check command (`npm run build`, `cargo test`, `uv run pytest`…), the current Tailwind 4 facts (no `tailwind.config.js`, `@theme` in the CSS) the 7B gets wrong, and the user's standing rule for new projects: SOLID and YAGNI. The generator's starter files are registered as read, so the model can replace `page.tsx` whole. A missing toolchain (`composer`, `dotnet`…) is reported before anything runs.

Calls made before the model's first turn (`agent.ts`): files the request names that exist (quoted, absolute, `~`, drag-and-drop paths with escaped spaces, including macOS screenshot names whose narrow no-break space before "AM" the terminal doesn't escape, and paths typed with plain spaces; relative with an extension; at most three) are read with `read_file`, since a small model often answers "I don't have access to the file" instead (documents whole, since the answer can be on any page; code 150 lines); projects below the folder (three levels down, with a manifest or `.git`) whose name holds a word of the request are pointed out in the request ("the readiness portal" → `inspire_africa/inspire-readiness/`); "analyse/understand the X project" runs `project_overview` on the folder named, and so does a progress question ("where did we stop on the readiness portal?", "what's left?") on the project it names, else the folder, since the overview's latest commits say where the work stopped; a request that wires in an external service or API ("add Google sign-in with Firebase to the Flutter app") searches its docs, and one that upgrades, migrates, installs or sets up a named technology also checks its latest version. Ordinary building with a framework the model knows ("add a settings page to the Flutter app") looks nothing up. A request for a project that isn't here ("create a web page … using nextjs, create the project", "a FastAPI service", "start a new project") gets a hint to start with `create_project` (with the framework it names) and to build it with tools, SOLID and YAGNI; inside a project of another kind only when the request says "new". UI guidance follows the stack the request names ("using nextjs and tailwindcss" → React components with Tailwind classes), not only the folder's. The search query is only technology names and the kind of task ("flutter google sign-in firebase documentation"), never the request's words, so client names and plans don't reach the search engines. They show as ordinary tool rows and save a model turn (15–40 s on a CPU). After them the request is repeated as the last message: seen live, with the request above two long results, the 7B answered with a made-up `<tool_response>` block, which now also counts as no answer.

Deliberate omissions: no `apply_patch` (exact-match `edit_file` is more reliable for small models), no separate `run_tests`/`run_linter` tools (the project's detected commands are in the system prompt and run through `bash`, which records test outcomes), no `git_push`.

## MCP servers (`mcp/`)

A hand-written MCP client (no SDK dependency) that speaks both protocol eras. `config.ts` reads `mcpServers` from the user's config and the project's `.mcp.json` (only in a trusted folder) in Claude Code's format, expands `${VAR}`/`${VAR:-default}`, and checks each entry. `transport.ts` moves JSON-RPC messages: stdio (newline-delimited on a child's standard streams, its own process group, `childEnv()` plus the server's `env`, stderr tail kept for errors, stdin closed then SIGTERM then SIGKILL on close), Streamable HTTP (one POST per message, answered with JSON or a request-scoped SSE stream; the 2025 revisions' `Mcp-Session-Id` kept and ended with DELETE) and the deprecated HTTP+SSE (GET event stream, POSTs to the endpoint it names, same origin only). `client.ts` speaks MCP:

- **Era detection**. Modern servers (2026-07-28) have no handshake: every request carries `io.modelcontextprotocol/protocolVersion`, `clientInfo` and `clientCapabilities` in `_meta`, and on HTTP the `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` and `Mcp-Param-*` (from `x-mcp-header` in a tool's schema, base64-sentinel encoded when not plain ASCII) headers. Ngobe probes with `server/discover`; a modern error (`-32020`…`-32022`) means a modern server (an unsupported version is retried with one from its `supported` list, which may mean initializing with a 2025 version), anything else means a legacy server (2024-11-05 … 2025-11-25), which gets `initialize` + `notifications/initialized`. On stdio a legacy server may not answer the probe at all; after 5 s `initialize` goes out too and whichever handshake succeeds first decides (a slow `npx` start reads both in order). On HTTP a non-modern 4xx falls back to `initialize`, and a 400/404/405 to that to HTTP+SSE.
- **Requests**: `tools/list` page by page (`nextCursor`), `tools/call`; `resultType` absent or `complete` is a result, `input_required` (MRTR) is reported as input ngobe can't give, since it declares no sampling, elicitation or roots. Legacy servers' pings are answered and their other requests refused with `-32601`. A cancelled or timed-out call sends `notifications/cancelled` on stdio and closes the stream on HTTP. A stdio server that exits is restarted on the next call (three times a session at most); a 2025 session the server forgot (404) gets one new handshake.
- **Tools** (`tools.ts`): `mcp__<server>__<tool>` (Claude Code's names, so a custom agent's tool list works in both; sanitized to 64 characters with a hash when cut), label `server - tool (MCP)`, the server's input schema without `$schema`/`title`/`examples`/`x-mcp-header` (lean profile: descriptions cut to a sentence), risk `network` for `readOnlyHint` tools (offered in ask/plan modes, no approval) and `write` otherwise (approval in edit mode; `destructiveHint` → explicit every time; `autoApprove` → none). Results: text items joined, images/audio as placeholders with their type and size, resource links and embedded resources as text, `structuredContent` as JSON when there is no text, `isError` as a tool error the model sees. The agent's usual timeout (`toolTimeout`), output limit and audit logging apply.
- **Session** (`index.ts`): `McpManager.start` connects every server in parallel during `createSession`, next to the project scan; failures are warnings, never a stop. Tools go after the built-in ones sorted by server and name, in both profiles, so the tool list (part of the prompt prefix llama.cpp caches) is the same from session to session. `/mcp`, `ngobe mcp list|get|add|remove` and `ngobe doctor` show each server's state, tool count and approximate prompt-token cost. Benchmarks run without MCP.

## Live knowledge (`releases/`, `web/`)

- `releases/versions.ts`: one resolver per official source; distinguishes stable from beta/dev/pre-release channels; returns version, date, channel, source URL and fetch time. Unknown names must be given an ecosystem rather than guessed.
- `releases/installed.ts`: versions on PATH (fixed commands, no shell) and in the project (node_modules, pubspec.lock, FVM pins, composer.lock, pip).
- `releases/notes.ts`: GitHub releases → repository CHANGELOG → changelog page linked from the registry, or the official docs page for language runtimes; `since` lists every release after a version with lines that mention breaking changes, removals or deprecations.
- `releases/advisories.ts`: OSV.dev (aggregates GitHub advisories, PyPA, Go, RustSec and others).
- `web/http.ts`: timeouts, size limits, retries with backoff (Retry-After honored), disk cache revalidated with ETag/Last-Modified. A cached answer keeps its original fetch time, so "checked" is never newer than the data.
- `web/search.ts`: Brave, Tavily, SearXNG; tried in order only when one fails or finds nothing; official domains rank first; results cached an hour.
- `web/net.ts`: `fetch_url` only fetches public http(s) hosts, re-checking every redirect hop; loopback, private, link-local (cloud metadata) and similar ranges are refused.
- Official pages fetched with `fetch_url` are indexed in SQLite FTS5 so `search_docs` still works offline, labeled with their fetch time.

## Chat UI (`tui/`, `lineUi.ts`)

The ink screen has an animated banner (`tui/logo.ts`: the letters build up, then a light sweeps across every few seconds, continuously while working; a one-line banner on small terminals), a scrollable transcript (tool calls as `⏺ Label(target)` / `⎿ summary` rows updated in place, replies rendered as markdown), a status line (`✻ Running tests… (34s · 2.8k tokens · esc to interrupt)`), the todo list, and the input with a `/` command menu (`slash.ts`). One clock (`tui/clock.ts`) drives every animation and only ticks while something moves. One-shot runs print the same tool rows and a spinner line in the terminal, and plain text when piped.

The screen uses the terminal's alternate screen (no scrollback for old frames to pile up in) and SGR mouse reporting: Ink drops mouse reports before `useInput`, so `App` reads wheel events from a `data` listener on stdin and scrolls only the transcript.

Folder trust (`trust.ts`) is asked once per folder, before the project's files are loaded.

Menus and questions: `Ui.select` (single or multi-select, with an optional second key such as `/model`'s `s`) and `Ui.input` are optional on the Ui interface. The ink screen draws a select as a bordered panel above the prompt (↑/↓ or j/k, space checks, a digit chooses, enter, esc cancels; long lists scroll around the cursor) and takes an input's answer from the prompt box (enter answers instead of sending a request); `LineUi` prints a numbered list. Commands still take text arguments where a Ui has neither (one-shot runs, tests). `/model` is a picker of the endpoint's models (`describeModel`: parameters, size and context from llama.cpp's `meta`): enter switches and saves the default, `s` switches for the session only, as in Claude Code. `/agents` (`agentWizard.ts`) is Claude Code's wizard: the agents by scope, **Create new agent** (location → generate with the current model or write by hand → tools: all, the read-only/edit/execution/MCP groups or single tools → model: inherit or one of the endpoint's → color → save), and view/edit tools, model or color/delete for an existing one. Generation is one short, non-tool request asking for JSON (name, description, prompt); `parseGenerated` takes a fenced or bare object and Claude Code's own key names too. Files are written in Claude Code's format (`agents.ts` `formatAgent`; edits change only the field asked for, so Claude Code's other fields stay), and `reloadAgents` rebuilds the `task` tool in place, so new and changed agents work without a restart. A sub-agent runs on its `model` (`agentModel`: inherit and Claude Code's model names mean the main model; `LLM.withModel` makes a client for the same endpoint), and its tool rows are drawn in its `color`.

## Permissions (`permissions.ts`)

| | ask / plan | edit | auto |
|---|---|---|---|
| read, search, version tools | run | run | run |
| plain read-only shell (`ls`, `cat file`, `git diff` …) | not offered | run | run |
| file writes, ordinary commands | not offered | ask ("always" covers the tool, or for commands the program + subcommand, e.g. `npm test`) | run |
| dangerous: delete, sudo, git push/commit/reset, installs, migrations, deploys, secrets, writes outside the project | not offered | ask every time | ask every time |
| fetch of a non-official site | ask | ask | ask |
| `remember` (memory writes) | not offered | ask (can be "always") | run |

Without a terminal, every "ask" is a deny. The shell classifier is a heuristic, not a sandbox: run `auto` mode in a container or a disposable checkout.

## Memory and learning (`memory/`, `learn.ts`, `bench.ts`)

- Facts carry project scope, provenance (`agent`, `observed`, `user`), confidence, timestamps and expiry (version facts: 7 days). Repetition raises confidence; failure lowers it. Values that look like credentials are refused. No source files or conversations are stored.
- Outcomes: every run records duration split into model and tool time, tokens, tool calls/errors and whether tests passed. Successful test/build commands are learned automatically.
- `NGOBE.md` (`projectMemory.ts`, next to `config.json`): About you (what the user asked to remember), Lessons, and Projects (what each is, from its manifest, and a dated log of every run that used tools, filed under the project the run changed or looked at). The relevant part (the user, lessons, this project's recent log, the projects inside this folder) is in each session's context. Sections the user adds are kept.
- Resuming: a record of the current run (request, steps, changed files, outcome, last reply) is saved after every tool call under the folder and each project it touched (`stateDir/projects/*.json`). "where did we stop?" / "continue" / "resume" in a new session adds it to the request; a run that never finished (crash, lost connection) is continued, not redone. Chats without tool calls don't overwrite it.
- Feedback: a message that corrects the previous answer ("you didn't give the version", "no, the installed one", "it still doesn't work", "don't …") is saved to NGOBE.md's Lessons with the request it corrects, for every later session.
- Building UI (`design.ts`): a request to build or reproduce a UI gets design guidance on the user message (the project's framework from its stack, faithful reproduction, a 4/8 px spacing scale, states, accessibility, complete files); when an image is involved, the vision model is asked for a blueprint (layout, every element in order with its text, colors, size and rounding, typography, spacing) instead of a caption, and the image's palette is measured from its pixels with ImageMagick. ctrl+v in the chat (`clipboard.ts`) saves a clipboard image (AppleScript on macOS, wl-paste/xclip on Linux) and puts its path in the prompt.
- Images (`vision.ts`): with `visionModel`, `read_file` sends an image (PNG/JPEG as is, anything else or anything over 1.5 MB converted to a ≤1,280-px JPEG with sips or ImageMagick) to the vision model with a "transcribe all text exactly, then describe" prompt; the coding model reads the answer. Without one, or if it fails, tesseract OCR when installed.
- Lessons: when a tool call fails and a later call of the same tool with other arguments works, the pair is remembered for every project (`kind: lesson`, 180 days; the latest per tool) and shown in the session context of later sessions, e.g. `"github projects are named owner/repo" with {"name":"flutter","ecosystem":"github"}; worked with {"name":"flutter"}`. A retry with the same arguments (a flaky network) teaches nothing.
- Recurring failures are clustered without labels: error text is normalized (paths, numbers, quoted values, hashes) and grouped by token similarity. Clusters seen 3+ times in a project are shown to the model as warnings, and in `ngobe learn` and `doctor`. A cluster is a pattern, not a proven cause.
- Retrieval signals: search results the agent goes on to fetch raise that source's standing.
- Prompt variants replace only the "How to work" section. Mode rules, freshness rules, trust rules and all permission checks are fixed in code. `ngobe learn propose` asks the model for a candidate; `ngobe benchmark --variant x` scores it; `ngobe learn promote x` requires results with the current model, every must-pass (safety) task passed, and a score at least that of the prompt in use; `ngobe learn rollback` restores the previous one.
- The benchmark (`src/benchData.ts`: tasks and fixture projects, carried inside the binaries too) checks answers deterministically: expected versions are fetched from official metadata at evaluation time, repo tasks must make the real test command pass without editing protected tests, injection tasks fail on any attempted unsafe action (even a blocked one).

## Security model

- Untrusted inputs: model output, tool arguments, file contents, web pages, search results, memory notes. Tool output is never parsed for tool calls; the system prompt tells the model that tool output is data; web content is labeled untrusted.
- Workspace: file tools resolve paths inside the project after following symbolic links (a cloned repo's `notes.txt -> ~/.ssh/id_rsa` is refused, as is an innocent name linking to a secret file); glob and grep don't descend into linked directories; git refs and paths are validated (no option injection). Writes under `.git/` need explicit approval, and read-only git commands run with `core.fsmonitor` off.
- Secrets: `.env*` (except templates, any letter case), keys, `.netrc`, `.npmrc`, SSH and cloud credential paths need explicit approval to read or write, are skipped by grep, left out of `git_diff`, and make any shell command that names them "dangerous", as does expanding a variable named like `*TOKEN*`/`*KEY*`. No program Ngobe starts (shell commands, git, rg, version probes, remembered test commands) inherits its own credentials (`NGOBE_API_KEY`, `NGOBE_SEARXNG_KEY`, `BRAVE_API_KEY`, `TAVILY_API_KEY`, `GITHUB_TOKEN`; `childEnv.ts`). Read-only git runs with `core.fsmonitor=false`, and `pip show` runs from an empty directory, so a planted `.git/config` or `pip/` folder in a project runs nothing. API keys come from the environment only; the config file can't hold them. Logs and memory are redacted field by field.
- Network: `fetch_url` and changelog URLs taken from registry metadata go through the same guard (public addresses only, in any IPv4/IPv6 spelling, every redirect re-checked); an auto-approved official URL can't redirect to another site.
- Memory the model writes (`remember`) is a write-level action, shown to later sessions as notes from the agent; `ngobe test` only runs remembered commands learned from passing runs, and asks first.
- Approval prompts strip terminal escape sequences and show control characters, so a command can't hide part of itself.
- The model endpoint and permissions come only from flags, the environment, or the user's config file; nothing in a project directory can change them.
- MCP: a project's `.mcp.json` starts programs, so it is read only in a trusted folder. MCP tool results are untrusted data like any tool output, and tool annotations are the server's claims: `readOnlyHint` skips approval only because the user chose to add the server. Server processes get `childEnv()` plus their configured `env`; an HTTP+SSE server can't redirect messages to another origin.

The prefix is byte-identical across requests, so llama.cpp's prompt cache reuses it and later turns only process what's new. Opening the chat, measured on the same VPS with the model kept loaded (startup warm-up, 2026-10-20):

| | ready after |
|---|---|
| first session after the model loads | 68.5 s |
| another folder | 3.2 s |
| back to the first folder | 5.1 s |

Before the session context moved out of the system prompt, every new folder, day or mode cost the full ~68 s. Model latency dominates on CPU; measure it on the target with `ngobe doctor` and `ngobe benchmark`.
